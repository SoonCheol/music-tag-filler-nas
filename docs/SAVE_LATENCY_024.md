2026-10-28 (Asia/Seoul). GitHub push 및 운영 음악을 이용한 저장 테스트는 수행하지 않았다.

## 결론

실제 가사 저장 13.0258초 사례는 확인했으나 동일 NAS 볼륨의 생성 음원으로는 재현되지 않았다. 사용자는 해당 저장에서 커버 체크가 꺼져 있었다고 확인했다. #020 최적화/안전 처리 변경이 13초의 원인이라고 확정할 수 없으며, 이번 배포로 13초 문제가 해결됐다고 주장하지 않는다.

확인된 중복 처리만 제거하고 다음 실제 저장에서 병목을 확인할 로그를 추가했다. 최초 원본 백업, 리비전/무결성 검사, 파일 fsync, 게시 디렉터리 동기화, 실제 바이트 복원은 유지했다.

## 변경

- app/job_store.py: storage._replace_file이 이미 수행한 부모 디렉터리 동기화를 중복 호출하지 않는다. 기록 한 번당 디렉터리 동기화 2회 → 1회.
- app/main.py: 저장 완료 후 save_jobs(job_id)로 해당 작업만 직렬화한다. lock_wait/file_save/job_record 시간을 save_timing 로그로 남긴다.
- app/storage.py: 저장 단계와 fsync가 0.25초 이상 걸릴 때 save_storage_timing 로그를 남긴다. 가사 본문을 기록하지 않는다. 기존 저장 동작 및 실패 전파는 유지한다.
- tests/test_p6_job_store.py: 중복 동기화, 동기화 실패/재시도, 다른 작업 직렬화 제외 및 로그 검증.
- tools/benchmark_save_latency.py: 운영 경로를 마운트하지 않는 생성 음원 비교 도구.
