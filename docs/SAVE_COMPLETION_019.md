# #019 저장 완료와 후속 처리 오류 구분

기준: `c1fbc4d` (#018). NAS 배포와 GitHub push는 실행하지 않았다.

## 변경 사항

- 검증한 스테이지의 SHA256과 실제 음악 상태로 게시 완료를 확인한다. 음악 게시 뒤 발생한 오류, LRC 발행·저널 완료 오류, 이름 변경 후 동반 파일·alias·작업 경로 기록 오류, 결과 읽기·응답 생성 오류는 완료된 저장을 `failed`로 바꾸지 않는다.
- 기존 `saved`/`partial`/`failed`, `warning`, `rename_error`, `state_error` 구조를 유지한다. `music_saved`, `postprocess_errors`, `recovery_pending`을 부가 정보로 제공한다. 기존 UI는 저장 건수와 일부 처리 건수, 음악 저장 완료 안내와 후속 오류를 표시한다. UI 소스 변경 없음.
- 실제 음악 쓰기 실패와 이름 변경 전용 작업의 실제 이동 실패는 `failed`다. 후속 처리 실패 시 음악 리비전이 달라졌거나 경로를 검증할 수 없으면 성공으로 간주하지 않는다.
- LRC 최초 실패도 디스크의 pending 저널에 오류를 기록한다. 오류 기록 자체가 실패하면 기존 저널을 보존한다. 이름 변경은 기존 저널·no-replace·파일 정체 검증·전진 복구를 사용한다.
- 재시작 시 기존 rename/LRC 복구가 안전하게 완료된 다음, 실제 파일과 일치하는 저널만 근거로 파일별 저장 상태·현재 리비전·작업 요약을 복원한다. 경로 복구가 차단된 경우에는 상태 복원도 진행하지 않는다. 미완료 후속 작업 복구 중 음악 재저장·음악 재이동이 없는지 검사한다.

## 로컬 검증 (2026-10-26, Windows)

실제 음악과 NAS data는 사용하지 않았다. ffmpeg로 임시 MP3/FLAC/M4A/OGG를 생성했다. 기존 임시 의존성 디렉터리를 사용했으며 프로젝트 의존성을 변경하지 않았다.

Python 대상: `test_p0_storage`, `test_p13_storage_failures`, `test_p14_storage_rename`, `test_p15_alias_sidecar`, `test_p16_path_recovery`, `test_p17_save_completion`.

- 112개 실행: 정상 통과 110개, 건너뜀 1개, 기존 예상 실패 1개.
- 새 #019 검사 13개: 게시 전/후 예외, 결과 읽기 오류, 실제 저장 실패, 이름 변경 전용 이동 실패, 파일별/최종 응답 생성 오류, 작업 상태 직렬화 오류, LRC 복구 성공·충돌 실패, 이름 변경 후 작업 경로 기록 실패와 재시작, 음악 게시 직후 중단과 재시작.
- 기존 P0의 저장 후 읽기 오류 HTTP 검사를 expectedFailure에서 정상 회귀 검사로 전환했다. 4형식 원본 복원·오디오/백업 보호 검사 유지.
- Node `tests/test_ui_save.js`, `tests/test_p2_ui.js` 통과. Python 문법 및 이번 변경 파일의 `git diff --check` 통과.

Windows 하네스는 `unittest.mock.patch`로 `rename_service.no_replace`를 Windows의 덮어쓰기 없는 `os.rename`으로 대체했다. `rename_service.sync_dir`와 `os.fsync`는 대체하고, `os.pathconf`는 255, `os.statvfs`는 쓰기 가능 값을 제공했다. 이는 애플리케이션 계약 검사이며 Linux 내구성 검증이 아니다. 하네스는 임시 디렉터리에만 두었고 운영 코드에는 플랫폼 우회 처리를 추가하지 않았다.

추가 P2 전체 실행에서는 옵션 기본값 기대치(`use_fingerprint` 누락) 불일치 1건과 Windows 심볼릭 링크 권한 오류 3건이 확인됐다. 옵션 실패는 `git archive --format=zip c1fbc4d`로 추출한 별도 임시 기준 코드에서도 동일하게 재현됐다. 요청 범위 밖 옵션/권한 코드는 수정하지 않았다.

## 남은 검증과 제한

- Linux `renameat2` no-replace, 실제 파일/디렉터리 fsync, 읽기 전용 검증 마운트, 프로세스 강제 종료 및 NAS 통합 검증은 #020 대상이다. 읽기 전용 마운트 검사는 이번 실행에서 건너뛰었다.
- 기존 예상 실패 1건은 upstream `tags.rename_file`을 직접 호출하는 저널 없는 레거시 sidecar 롤백 잔여 복구다. 현재 앱의 자동 이름 변경 경로는 저널 기반이며 해당 호출로 우회하지 않는다.
- 일반 태그 단독 저장 직후 강제 종료되어 rename/LRC 저널이 없는 경우는 기록만으로 완료를 확정할 수 없으므로 임의로 성공 처리하지 않는다. 재스캔으로 현재 리비전을 확인해야 한다. 새 범용 음악 저장 저널은 추가하지 않았다.
- 저장 결과 읽기 또는 작업 상태 기록 자체가 실패한 경우 현재 파일 리비전을 다시 읽거나 복구한 후 재시도해야 할 수 있다. 검증되지 않은 파일을 덮어쓰기·이동·삭제하는 방식으로 재시도하지 않는다.
- 기존 사용자 수정 `AGENTS.md` 및 Aider 기록은 커밋에 포함하지 않는다. 전체 diff 검사는 기존 `AGENTS.md` 공백 오류를 보고하므로 이번 변경 파일만 별도로 검사했다.
