# 직접 파일명 변경의 복구 기록

직접 이름 변경은 Linux renameat2(RENAME_NOREPLACE)만 사용하며 미지원 시 실패합니다. 원본 음악 바이트와 수정 시간은 변경하지 않습니다. 파일명 변경으로 태그 저장 상태를 바꾸지 않습니다.

프로그램 data의 `renames/`에는 순번, 이전/새 경로, 파일 리비전·정체, 백업 연결과 처리 상태가 기록됩니다. **jobs.json·backups와 renames를 함께 보존해야 합니다.** 이름 변경 중 서버가 중단되면 시작 시 실제 파일·백업을 확인하고 새 이름 기준으로 작업 기록을 복구합니다. 파일 변경 전 중단된 경우 기존 파일을 유지하며 미실행으로 기록합니다. 양쪽 이름에 파일이 있거나 정체가 불명확하면 변경 작업을 차단하며 원본을 임의 삭제하거나 되돌리지 않습니다. 오류가 남으면 실제 경로와 기록을 확인해야 합니다. 기록 파일을 임의 수정·삭제하지 마세요.

기존 최초 백업 ID와 내용은 보존하며 `.tagbak.json`을 같은 이름으로 옮기고 중앙 백업에 검증된 경로 별칭을 추가합니다. 태그·가사·커버를 다시 기록하지 않습니다. 기존 자동 파일명 변경 옵션은 그대로이며, 이후 태그 저장에서 옵션이 켜져 있으면 직접 지정한 이름이 다시 자동 변경될 수 있습니다.

경로 변경 알림은 기존 폴링을 통해 전달합니다. 대상 곡의 재생/일시정지와 URL 참조만 해제하며 자동 재생하지 않습니다. 선택·체크·미저장 초안·표시 순서는 유지합니다. 다른 탭·브라우저는 폴링 후 반영하며 백그라운드 탭이나 연결 끊김으로 지연될 수 있습니다. 서버 재생 세션·WebSocket은 사용하지 않습니다.

앱 내부 작업은 기존 음악 작업 잠금과 진행 중 검색 등록, 저장 대기열의 예약 검사로 충돌을 방지합니다. 다른 앱/SMB 클라이언트의 동시 변경까지 잠글 수는 없습니다. 정확한 대상 이름은 커널이 덮어쓰기를 차단하고, 대소문자·유니코드 정규화 충돌은 변경 전 폴더 항목 검사로 차단합니다. 외부 앱에서 같은 폴더의 이름을 동시에 변경하는 작업은 피하세요.

배포 입력: `app/rename_service.py`를 deploy-nas.ps1 허용 목록과 기존 app Docker context에 포함합니다. 의존성 추가는 없습니다.

## #016 자동 이름 변경 통합 (로컬 작업본)

태그 저장의 자동 이름 변경도 위 저널·no-replace·전진 복구 경로를 사용합니다. 음악·sidecar·LRC가 이동 직전에 생성되면 기존 파일을 보존하고, pending 기록이 남으면 후속 쓰기를 차단합니다. 여러 파일 이동 전체가 하나의 원자적 작업인 것은 아닙니다. 기존 번호 붙이기와 최초 백업 ID를 유지하며 기존 무저널 실패 잔재는 자동 수정하지 않습니다. 손상되거나 해석할 수 없는 rename/LRC 저널이 있으면 복구 이동을 시작하지 않고 쓰기를 차단합니다.

이번 변경은 NAS에 배포하지 않았습니다. Windows 보조 검증의 결과·환경 오류와 Linux 미검증 범위는 STORAGE_REFACTOR_PLAN.md의 #016 기록을 따릅니다.
